# tow-query

Translate natural language into reproducible searches: **one tow search query → list the matches → open only the notes you describe**. Read the [conventions](../../docs/methodology.md) and start with `tow config`; no setup, PARA, frontmatter or dictionary is required for host file search.

From a project, search both the connected vault and the current project, unless the user names only one of them ("in my vault", "in this repo"); then search only that source and skip the other's file listing. Inside the vault, search the vault only; never search project documents from there. Results state their source (`vault` or `project`) and path. This skill is read-only.

`tow` is not a command on your PATH: run the executable `scripts/tow.py` two directories above this file by its absolute path (with `python3` if the host can't execute it), for example `"<plugin-root>/scripts/tow.py" config`.

## Workflow

1. **Establish scope before reading.** Run `tow config` and use the vault root/source it reports; never infer the vault from Obsidian's active vault. From a project, resolve the project scope and its `.tow/` configuration when present. Follow the conventions' private/ignored rules before content reads. Inside the vault, search only its authorized scope. Never search the project from a vault session.
2. **Interpret the recollection.** Identify the topic, likely terms/aliases, relevant tags and requested conditions. A topic may match concepts, text, title, properties or links; don't assume a TOW schema. Consult the configured vault tag dictionary (normally `tow/tag-dictionary.json`) when available and relevant for canonical concepts, aliases and narrower concepts. For likely tag candidates, use `tow ontology show <tag> --json` to inspect the broader chain and consider relevant parent concepts too. Ask for the user's memory if the query remains too vague to search usefully. `tow search` resolves tags, aliases and narrower tags itself, so do not grep the tag dictionary first; read `tow/categories.md` or the category dictionary only when the request names a category or classification condition.
3. **Run one search.** Run `tow search "<query>"` once with the terms and conditions from step 2. A bare word matches a concept (tag, alias or narrower tag), a title, a heading or the body; `tag:x` (with aliases and narrower tags; `tag:=x` for the tag alone), `title:`, `heading:`, `text:`, `path:`, `category:` (prefix), `type:`, `status:`, `kind:` and `source:vault`/`source:project` narrow a clause. A space is AND, `OR` is OR, `-` excludes, `( )` groups and `"…"` is a phrase; use one query for an intersection or a union instead of several calls. It applies the configured scope, project archives and Git ignore rules itself, so do not run `tow lookup`, `tow find`, `rg` or a dictionary grep before it. Its JSON lists every match with `reasons` (the clause and its kind, such as `exact`, `narrower`, `title`, `text`). When `warnings` is not empty, compare `query.interpreted` with what you meant; if they differ, run `tow search` once more with the warning's `retry` or your own fix. An entry under `unavailable` is a search that did not run (for example concepts when npm is blocked, or body search when Git is missing): report it, and cover only that part with step 4. Exit 1 means no match in what ran, not proof of absence when something is under `unavailable`.
4. **Host file search only for gaps.** Use host file search only for what `tow search` listed under `unavailable`, or for project files it did not cover (an unregistered project). List file names first, for example `rg -l -i '<terms>' <scope folders>`, in the scope `tow config` reports: with `"scope": "para"`, only the four PARA folders, skipping project archive folders and the inbox; with `"scope": "vault"`, the whole vault. Never search `tow/` or `.tow/`, and apply the private/ignored rules before any content search. In an unregistered project, list file names only within the user-authorized scope and read untracked or ignored files only when the user selects them.
5. **Optional Obsidian CLI.** It is only a read-only vault search accelerator. Always name the confirmed vault and explicit path, for example `obsidian vault="<vault name or id>" search path="<folder>" query="<terms>"`, `obsidian vault="<vault name or id>" search:context path="<folder>" query="<terms>"`, or `obsidian vault="<vault name or id>" read path="<vault-relative path>"`. Use no other CLI commands: never `eval`, `create`, `delete`, `move`, `rename`, `append` or `prepend`. A folder argument is not an OS permission boundary; obey the host's access rules and use scoped host file tools if the CLI cannot enforce the content exclusions before reading.
6. **Fallback and access errors.** If `tow config` reports no vault, do not guess: fall back to scoped host file search only in a folder the user names. If none is named, ask for one. If the host denies vault access, print the applicable setup hint and stop; do not retry through shell, Obsidian CLI or another tool. Claude Code: `Read(//<vault>/**)` or `permissions.additionalDirectories`; Codex: reads outside the workspace are not blocked by the default sandbox; Antigravity: `read_file(<vault>)` permission rule. Writes are not needed for this skill. This is a skill-level rule, not an OS-level access boundary.
7. **List, then open what you describe.** First list every match by title, path, source and match reason (exact tag, alias, narrower concept, broader concept, title, text) from the lookup and file-name results, without opening bodies. For a topic request ("find my notes about X", "what do I have on X"), open at most five notes, exact and narrower concept matches first, then title matches, and describe each in one line; say how many listed matches you did not open and offer to open more. For a specific recollection ("where did I save X?"), open candidates in that order until one is confirmed, then ask, “Is this the one?” Check requested predicates (dates, properties, counts) on the content of every note you report as meeting them. Keep helper-verified exact/alias/narrower concept matches separate from broader-concept or text-only inferred candidates. Missing properties are unknown, not guessed. Say “no matches within the checked scope” only after both applicable concept and text searches were checked. Mark partial scope, errors and unopened notes; this skill writes nothing.
8. **Describe only what you opened.** A note you did not open is listed by title, path and match reason only, never summarized. Return the output below.

## Output

- Briefly state the interpreted conditions and effective scope; include the executed query/method when useful for reproducing the result.
- List title, path, source, match reason and requested fields, and mark which notes you opened. Separate verified exact matches from inferred candidates and explain unknown fields/evidence.
- Give the number actually listed; distinguish total verified matches from a displayed limit. Mark incomplete scans, tool errors, excluded paths and uncertain fields. Say "no matches within the checked scope" only after the fallback/verification supports it.
- Group a domain survey by subtopic when helpful. A category with no retrieved notes is a confirmed gap only after applicable search coverage is verified.
