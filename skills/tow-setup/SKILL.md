# tow-setup

Read the [conventions](../../docs/methodology.md). Branch on the current location: run `tow config` and use its reported vault root/layout; if no vault is resolved yet, use `tow --root <vault> config` only for a vault path the user identifies. In a project, register the project and vault connection without changing host configuration. Current vault files live in visible `tow/`; project metadata remains in `.tow/`.

## Workflow

1. **Inspect names and settings first.** Determine whether the current folder is inside a `tow/` vault, an older `.tow/` vault, a legacy vault (`tow.json`, a non-empty `Tag-Dictionary.json` or `Category-Dictionary.md` at its root), or a project. An empty root `Tag-Dictionary.json` (`{}`) by itself is the plugin's starter, not a legacy marker; if `tow init` reports it, initialize the `tow/` layout and do not delete the root file. Inspect folder/file names and configuration; don't read project document contents as setup input. Never infer a vault from `.obsidian` or the active Obsidian vault.
2. **Inside a vault.** If `tow/`, `.tow/`, or a legacy vault is already recognized, report its effective configuration. Otherwise ask whether the user wants TOW setup, their chosen PARA/custom layout, and which optional dictionaries they want; no preference is inferred from folders. For a new vault with no marker, target it explicitly with `tow --root <vault> init` and show every path it proposes. Apply with `tow --root <vault> init --apply` only if the user approves the complete preview; pass `--dictionaries` when the user chose dictionaries in a free-form vault. For a custom layout, first propose the exact `tow/config.json` settings (including `"scope": "vault"` and chosen folder/dictionary paths) and selected starter files. Preview with `tow --root <vault> init`; after approval, use `tow --root <vault> init --apply` only if its complete preview matches the approved plan; otherwise create only the approved subset with file tools, preserving existing files. Never create a dictionary just to satisfy a helper check. For a request to move existing TOW files, or when a legacy/`.tow/` config prints its migrate hint, first update the Tag Ontology plugin to 0.10.1 on every device, then preview `tow --root <vault> migrate` and apply only after approval with `tow --root <vault> migrate --apply`. Keep old files by default. Migration carries root `Tag-Dictionary.md` into `tow/tags.md` and the Markdown category rule document into `tow/categories.md`; tell the user to update notes that link to those old files if they later remove them. Only after the user confirms plugin 0.10.1 is installed on every device may you offer removal as a separate approved plan: preview `tow --root <vault> migrate --remove-legacy`, then apply with `tow --root <vault> migrate --remove-legacy --apply` only after approval and verification.
3. **Record the connection.** Show `tow connect <vault>` and wait for approval before `tow connect <vault> --apply`; confirm with `tow connect`. It writes the user's personal `~/.tow/config.json`, never a project file. Outside a vault, `TOW_VAULT` overrides the saved connection. Inside a vault, the nearest ancestor vault takes precedence over both personal connections; use `--root` for an explicit choice. Setup does not edit host configuration.
4. **Set up from a project.** Determine the project root and `tow config` vault connection. If no vault is connected, ask the user to set up the vault first. Ask whether project `.tow/` metadata should be local or shared. Before project registration, inspect root/folder names only with host file tools to identify dependency/build folders; propose excludes only for folders actually found (for example `node_modules`, `vendor` or `dist`) and get approval. Show the complete vault `tow/tags.md` manual text before copying it; ask for any desired edits to remove private notes. Preview `tow project init --mode <local-or-shared> [--exclude <glob> ...]` as selected, then apply only after approval with `--apply`. This creates project `.tow/config.json`, `documents.json`, and the project tag dictionary/manual, and configures local Git excludes in local mode. After `tow project init --apply`, make any user-requested manual edits to the project copy `.tow/tags.md` before committing shared-mode metadata. After registration, use `tow project files` for names-only Markdown/Git-status discovery; list untracked and ignored paths before any content read, and read those only when the user selects them. It never writes project documents or stores the vault path in the project.
5. **Align the Tag Ontology plugin.** Read the warning line from `tow config`. If it says the plugin dictionary path differs or could not be checked, explain that plugin 0.10.1 auto-detects `tow/tag-dictionary.json`, then `.tow/tag-dictionary.json`, then the stored path unless a custom path was chosen. Tell the user to align the plugin's “Dictionary path” setting with the effective configured `tagDictionary` path (normally `tow/tag-dictionary.json`). Never edit `.obsidian/` settings.
6. **Print host access guidance.** Show only relevant snippets for the user's host; substitute the actual vault root and configured note folders. These are permission hints, not changes TOW makes:

   - Claude Code reads: `Read(//<vault>/**)` or `permissions.additionalDirectories`; send-vault writes: `Edit(//<vault>/<note folder>/**)` or per-call approval.
   - Codex reads outside the workspace are not blocked by the default sandbox; writes require configured vault note folders in `sandbox_workspace_write.writable_roots` or approval. Permission profiles are beta and do not cover MCP.
   - Antigravity: `read_file(<vault>)` and, only if sending is wanted, `write_file(<vault>/<note folder>)` permission rules.

   State that skills and TOW do not provide an OS-level access boundary; host tools and shell can have different permissions. Never bypass access denial or edit host settings/configuration.
7. **Verify and report.** Re-run the applicable `tow config`, `tow connect`, or `tow project status` and check only the approved setup changes. Confirm existing notes/project documents were untouched. Report skipped setup choices and the next useful `tow-query` or `tow-send-vault` action.
