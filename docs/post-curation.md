# User-guided post-curation

`tow-edit`, `tow-merge`, `tow-ingest` and `tow-review` are optional aftercare for already written notes. Ordinary metadata/format maintenance does not invoke body generation, consolidation or derivation automatically. Read the [preservation contract](preservation.md) first; these workflows add only the operation the user explicitly selected.

## Required inputs

- **Target:** exact notes, selected source batch or authorized review scope.
- **Operation:** inspect/propose, file verbatim, write a named empty section, move named content, merge a selected case, or another precisely stated transformation.
- **Rules:** a user-supplied template, vault instructions, an established applicable convention, or a concrete destination/heading plan the user chooses. Record its path/section or the user's rule. Folder names and a bundled TOW example do not establish a writing policy.
- **Boundary:** what may be added/moved/changed and what must remain verbatim. A template describes the result; it does not authorize rewriting filled sections, synthesizing claims, discarding facts or adding fields.

Inspect existing authorized rules before asking for missing information. If a rule needed for the selected transformation is absent or conflicting, ask only about that rule and keep notes unchanged. Do not silently select the bundled Resource/paper/prose template. A request for a file move with a named destination and verbatim body already supplies enough rules; do not demand an unnecessary writing template.

## Workflow contract

1. Start read-only. Record target, operation, rule source and preservation boundary. A review or cleanup request produces findings and a proposed plan, not body edits.
2. Show exact destinations/sections and the proposed before/after changes for selected body transformations. Prior explicit choices settle their stated scope. A clear empty-section writing request can proceed directly only when its rules/source and boundary are already supplied or established; preserve every filled section.
3. Preserve the source privacy/ignore boundary for every snapshot/candidate before copying, including failed or interrupted batches, as required by the preservation contract. Keep merge-by-merge strategy choices, separate discard confirmation, private-input rules and independent destination verification before deletion. Batch approval does not waive these decisions.
4. Preserve source material verbatim by default. New text belongs only in selected new/empty destinations under the chosen template and must be grounded in the selected sources; flag unsupported content rather than invent it. Any rewrite/summary of filled content needs its own explicit scope, not implied approval from an intake/review/template request.
5. Verify original-to-destination facts, protected math/code/table payloads, metadata and unrelated prose. Apply the [preservation checks](preservation.md) to the parts that were only formatted or classified. Report actual changes, skipped work, unresolved choices and verification limits separately.
